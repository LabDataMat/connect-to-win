# 玩法与关卡设计说明

## 1. 核心规则（唯一判定来源）

### 1.1 方向与旋转

方向用 4 位掩码表示：上 `1`、右 `2`、下 `4`、左 `8`。一个方块可以同时拥有多个开口（直管 `2|8`、肘形 `2|4`、三通 `1|2|8`、四通 `15`）。

顺时针旋转 90° 的映射为 `上→右→下→左→上`，等价于掩码左移一位（循环）：

```
N(1) → E(2) → S(4) → W(8) → N(1)
```

方块记录「解状态方向 `baseDirs`」与「当前旋转次数 `rotation ∈ 0..3`」，实际开口 `dirs = rotateCW(baseDirs, rotation)`。这样做的原因：

- 关卡数据只需存解状态，旋转是纯函数推导，不会出现「数据和显示不一致」；
- 提示可以精确算出某格还差几次旋转；
- 旋转 4 次必然回到原位，便于测试。

### 1.2 连通判定

两个**正交相邻**的格子 A、B 连通，当且仅当：

```
A 朝 B 方向有开口  &&  B 朝 A 方向有开口
```

只满足一侧不算连通；斜对角永不相连；空格（`null`）不参与连通。

### 1.3 通关判定

从起点做 BFS（`PathValidator.findPath`），能到达终点即通关。判定完全基于当前方块的开口方向：

- 与点击次数无关（不是「点了 N 次就算过」）；
- 与动画状态无关（逻辑在点击瞬间就更新，动画只是视觉表现）；
- 允许分叉：三通/四通方块只要形成任意一条从起点到终点的合法路径即可；
- 死路分支不会误判：BFS 走不通就返回 `null`。

### 1.4 步数与胜负

- 每次成功旋转 +1 步；点击空格、起点、终点不计步。
- 每次旋转后**先判胜**：若接通 → `won`；否则若 `moves >= stepLimit` → `lost`。
  因此「最后一步刚好接通」判为胜利，不会因为步数用尽而误判失败。
- `won` / `lost` 之后的所有点击都被忽略，不会污染步数与棋盘状态。
- 重试：`BoardManager.reset()` 把每个方块恢复到关卡初始旋转，步数归零，状态回到 `playing`。

### 1.5 分叉、死路、障碍、起终点

| 元素 | 规则 | 视觉 |
| --- | --- | --- |
| 起点 | 固定不可旋转，只有一个开口 | 琥珀色方块 + 闪电图标 |
| 终点 | 固定不可旋转，只有一个开口 | 品红色方块 + 同心圆靶心，接通后发光并出现射线 |
| 管道 | 可旋转；直管/肘形/三通 | 深色方块 + 青色导线，通电时高亮发光 |
| 干扰块 | 与管道同类型，但不在参考解路径上，用来制造干扰 | 与管道一致，不额外标记 |
| 绝缘块（空格） | 不可放置、不可点击，视为障碍 | 深色带斜线纹理的方块，保证棋盘结构完整 |
| 死路 | 允许存在，不参与判定 | 与管道一致 |

> 干扰块与死路都是「合法但无用」的方块。它们可能让玩家绕远路，也可能在极端情况下形成另一条合法路径 —— 按规则，只要能连通就算通关，这符合「存在合法连通路径即通关」的设计。

## 2. 关卡数据结构

```ts
interface LevelData {
  id: number;
  name: string;
  width: number;
  height: number;
  start: { x: number; y: number; dir: Dir };   // dir 为唯一开口方向
  goal:  { x: number; y: number; dir: Dir };
  cells: (CellData | null)[];                  // 行优先，长度 = width*height
  stepLimit: number;                           // 目标步数（上限）
  solutionPath: { x: number; y: number }[];    // 参考解路径（含起终点）
  difficulty?: number;
  daily?: boolean;
  dateKey?: string;
}

interface CellData {
  d: number;       // 解状态下的开口掩码
  r: number;       // 初始旋转偏移 0..3
  rot: boolean;    // 是否可旋转
  k?: TileKind;    // start | goal | pipe
}
```

`cells` 中的 `null` 表示空格。`solutionPath` 有两个用途：提示高亮、关卡校验的「解证据」。

## 3. 关卡生成算法（`src/core/LevelGenerator.ts`）

固定关卡与每日挑战共用同一套生成器，区别只在参数与种子：

1. **种子**：固定关卡用 `hashString('connect-to-win:level:<id>:<k>')`；每日挑战用 `hashString('daily:<YYYY-MM-DD>')`。PRNG 为 mulberry32，同种子结果完全一致。
2. **选端点**：起点固定在左边缘，终点固定在右边缘，行号随机。
3. **挖路径**：随机 DFS 找一条从起点到终点的简单路径，长度限制在 `[minPath, maxPath]`；强制第一步沿起点开口方向离开、最后一步从终点开口方向进入，保证开口始终朝向网格内部。
4. **铺管道**：路径内部格开口 = 「指向前一格」|「指向后一格」；起点/终点只有一个开口且不可旋转。
5. **加干扰块**：在非路径格子中随机放置肘形/直管/三通，初始朝向随机。
6. **打乱**：按目标成本定向分配——每个路径方块先给 1 次旋转，再随机加至 2~3 次，直到总成本接近 `1.9 × 内格数`。这样「参考步数」与路径长度成正比，不会因随机打乱出现成本暴涨/暴跌。
7. **算步数上限**：`stepLimit = 参考解所需旋转次数 + slack`。参考解所需次数 = 路径上每格「转回解状态还差几次」之和，因此**一定存在一条不超过上限的通关走法**。
8. **复检**：生成后立刻跑 `PathValidator.validateLevel()`，任何一项不通过就换种子重试（最多 60 次），**绝不返回无解关卡**。

每日挑战额外保证：同一 `dateKey` 两次生成结果字节级相同（测试覆盖）。

## 4. 关卡校验程序（`tools/validate-levels.ts`）

独立于游戏运行时的离线校验，`npm run validate` 执行。逐关检查：

1. 结构：尺寸、`cells` 长度、方向掩码 1..15、旋转偏移 0..3。
2. 起终点：在界内、不重合、只有一个开口、不可旋转、`start.dir`/`goal.dir` 与方块一致。
3. 参考解：从起点开始、到终点结束、每步相邻、不重复经过、经过的格子非空、每格开口方向满足前后两跳。
4. 初始状态不得已通关。
5. **应用参考解后必须真的连通**（这是「存在合法解」的实证，不是相信数据）。
6. `solutionCost ≤ stepLimit` 且 `solutionCost ≥ 1`。
7. 关卡之间不重复（用「方块方向序列 + 路径」作为指纹）。
8. 难度曲线不回退（网格面积、解路径长度、参考步数）。
9. 每日挑战：三个日期的两次生成结果一致、日期键计算正确、关卡合法。
10. 校验器自检（负例）：人为破坏解路径、删除解路径、把初始状态改成已通关，三种情况都必须被判定为非法。

真实执行结果见 [test-report.md](test-report.md)。

难度提升的三个来源：

1. **起终点不再固定在左右两侧**：起点/终点随机落在四条边中的任意一条，开口朝向网格内部，玩家每关都要先判断走向，而不是无脑从左往右推。
2. **棋盘几乎填满**：干扰块数量接近「非路径格」上限，中后期只留 2~4 个绝缘块，无法靠「空位」排除错误方向。
3. **步数余量收紧**：前期 +6 步容错，后期只留 +2 步，乱转就会失败。

## 6. 每日挑战

- 日期键：北京时间（UTC+8）的 `YYYY-MM-DD`，跨天边界已测试（`2026-10-29T15:59Z` → `2026-10-29`，`16:01Z` → `2026-10-30`）。
- 种子：`hashString('daily:' + dateKey)`，网格与干扰块数量也由种子派生（5×5 或 6×5、4~6 个干扰块）。
- 无服务器：客户端本地生成，因此**同一日期所有玩家谜题完全一致**，无需下发数据。
- 结果记录：`save.daily = { date, cleared, steps }`，同一天多次挑战保留更优成绩。
- 已知限制：种子算法公开，理论上可以离线算出答案；对休闲解谜影响可接受，若后续需要防作弊可改为服务端下发。

## 8. 最优解求解器与三星评价

### 8.1 为什么不能直接用设计步数

关卡数据里的 `solutionPath` 是一条**可行解**，`solutionCost` 只是「沿这条路径把每格转回解状态」的次数。它不保证最优：

- 直管有 180° 对称，转到 `r` 或 `r+2` 都能连通；
- 干扰块可能拼出比设计路径更短的通道；
- 设计路径本身可能不是最短路径。

修复前的实测：30 关里有 20 关的真实最优解不足设计步数的 72%（最夸张的一关设计 42 步，实际最优只要 8 步）——这正是早期版本「太简单」的根因。

### 8.2 双向旋转与最优解

- 顺时针、逆时针都只消耗 1 步，因此每格的代价是 `min(顺时针次数, 逆时针次数)`，最多 2 步。
- 求解器按这个双向代价计算 `minSteps`，并在 `steps` 里记录每一格该往哪个方向转；
  `verify()` 会按方向真实执行后复核连通性。
- 早期版本只允许顺时针，转错一次要 3 步才能回来，而步数上限只留 +2 余量 —— 一次误触基本等于失败。
  这是本轮修复的重点。

### 8.3 求解算法

`OptimalSolver`（`src/core/OptimalSolver.ts`）用 **DFS + 分支限界** 求精确最优：

- 状态：当前格 + 来路方向；路径不允许重复经过同一格（重复只会多花步数）；
- 边权：该格从当前朝向转到「同时提供来路与去路」的最小顺时针次数（0..3），开关关闭时额外 +1；
- 剪枝：当前代价 ≥ 已知最优即回溯；方向按「离终点的曼哈顿距离」排序，先找到较好的上界；
- 结果用 `verify()` 复核：按求解结果实际旋转/开闸，再用真实的连通性判定确认通关。

> 最初用的是 Dijkstra（状态 = 格 + 来路方向），但每个状态只能保留一条最优路径，
> 与「不能重复经过格子」冲突，导致 2 关漏解。改为分支限界后 30 关全部解出，
> 8×8 关卡耗时 < 15ms。

### 8.4 三星规则

| 星级 | 条件 |
| --- | --- |
| ★★★ | 步数 ≤ 最优步数 |
| ★★ | 步数 ≤ 最优步数 + max(2, ⌈最优 × 20%⌉) |
| ★ | 在步数上限内完成 |

- 星级只升不降：更差的成绩不会覆盖历史最佳星级。
- 已通关关卡可以无限次重玩，用于刷新星级。
- 重试只重置当前局面，不清除最佳成绩。
- 每日挑战同样按当天谜题的最优解评星。

### 8.5 闸刀开关（第四阶段新增）

- 开关不可旋转，方向固定；**关闭时 `dirs` 直接返回 0**，物理上不导电。
- 点击开关 = 切换开/关，消耗 1 步（与旋转同价）。
- 开关计入求解：关闭的开关在路径代价上 +1。
- 13 关起在解路径中段放置 1~2 个开关，初始为关闭状态。
- 视觉：两个固定触点 + 一根闸刀，闭合为绿色发光、断开为橙色翘起，另有状态灯。

## 8.6 每日挑战的连续记录

- 存档新增 `dailyStreak`（当前连续完成天数）、`bestDailyStreak`（历史最长）、`dailyHistory`（最近 30 天）。
- 连续判定：只有「上一天也完成」才 +1，否则重置为 1；同一天重复挑战不累加。
- 历史按日期去重，保留更好成绩（步数更少优先，其次星级更高），最多 30 条。
- 首页每日按钮显示「每日挑战 · 连续 N 天」，通关弹窗显示「连续完成 N 天」。

## 9. 屏幕适配

- 逻辑尺寸固定宽 750，最小高 1240；`scale = min(屏幕宽/750, 屏幕高/1240)`。
- 手机竖屏：按宽度铺满，高度自动变高；桌面/横屏/平板：按高度缩放，内容居中，左右留白暗化并画边界线。
- 渲染变换与点击反算共用 `computeViewport()`，保证「看到哪里就能点哪里」。
- 安全区按同一 scale 换算后叠加到顶部/底部内边距，刘海屏与 Home 指示条不会压住按钮。

## 10. 界面与状态机

```
home ──开始/继续──► game ──通关──► win 弹窗 ──下一关──► game
  │                  │  └──失败──► lose 弹窗 ──重试──► game
  ├──每日挑战──────► game(daily)
  ├──关卡列表──────► levels ──选关──► game
  └──设置──────────► settings ──清除进度──► 二次确认弹窗
```

- 弹窗打开时，背景元素不参与命中测试（`hitTest` 只接受 `layer === 'modal'`）。
- 切到后台：若在游戏中且无弹窗，自动打开暂停弹窗，并落盘存档。
- 所有按钮的点击区域由布局函数生成，与绘制共用同一份矩形，避免「看到的位置点不到」。
