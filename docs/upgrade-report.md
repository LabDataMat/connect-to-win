## 一、接手时的实际状态（基于代码核查，不是照需求推断）

### 1.1 技术栈说明

任务描述里写的是「Cocos Creator / TypeScript 项目」，但**实际代码不是 Cocos 工程**：

- 目录里没有 `assets/`、`*.scene`、`*.meta`、`project.json`，也没有 Cocos 运行时依赖；
- 渲染是自研的 Canvas 2D 层（`src/render/Renderer.ts`），入口是 `src/entry.web.ts` / `src/entry.wx.ts`；
- 本机未安装 Cocos Creator（第一轮已核实），因此当时选择了等价的纯 TypeScript 方案。

**结论**：按实际代码处理，没有虚构 Cocos 场景文件，也没有为了「看起来像 Cocos」而重写项目。

### 1.4 发现的主要问题

1. **关卡存在大量「捷径」**：独立求解后发现，30 关里有 20 关的真实最优解不足设计步数的 72%，最夸张的一关设计 42 步、实际 8 步就能通关。这是「太简单」的根因，光调步数上限治不好。
2. **没有最优解概念**：`stepLimit` 只是「参考解 + 余量」，`solutionCost` 也不是最优，三星评价无从谈起。
3. **电流反馈是静态的**：只有「从起点可达」的格子高亮，没有传播过程，玩家看不出电流走到哪、在哪断开。
4. **每日挑战不完整**：缺耗时记录、缺可分享的战绩图。
5. **统计缺项**：没有会话时长、首关完成等关键事件。

### 1.5 回归风险

- 关卡数据被重写（`levels.json`），旧存档的「最佳步数」会与新关卡的难度不匹配 —— 通过「星级只升不降 + 步数只记录更优」避免数据错乱，但旧的最佳步数可能偏松，属于可接受的历史数据。
- 求解器在关卡加载时同步执行（8×8 约 10ms），需要缓存，否则每次提示都会重算。
- 新增开关改变了 `Tile.dirs` 的语义（关闭时返回 0），所有依赖 `dirs` 的渲染/判定都必须同步。

## 五、体验改进

### 5.1 启动与性能

- 关卡数据从 31 KB 增至 47 KB，微信包 88.8 KB → 103.0 KB，仍然远低于 4 MB 上限，首包加载压力可忽略。
- 最优解按关卡缓存（`Map`，key = 关卡 id + 尺寸 + 日期），只在首次进入/提示时计算；8×8 实测 < 15ms，不会造成可感知卡顿。
- 电流动画、粒子、白闪全部是渲染层状态，**不参与任何判定**，也不改变输入时序；动画期间照样可以点击旋转。

### 5.2 操作反馈

- **电流传播**：每次有效操作后，电流从起点沿真实连通路径逐格流向终点（约 80ms/格，上限 900ms）；路径由 `PathValidator.findPath` 计算，**不会穿过断路**。
- **断路反馈**：未接通时电流停在最远可达格，闪一圈橙色光环后消失，不扣步、不弹窗、不打断操作。
- **通关反馈**：电流抵达终点 → 240ms 白闪 + 终点射线 + 粒子（粒子已移到弹窗之下，不遮挡文字）。
- **开关反馈**：闸刀闭合/断开有明确的几何差异（绿色贴合 vs 橙色翘起）+ 状态灯，不只靠颜色。
- 音效开关沿用设置页，静音后所有音效静默。

### 5.3 重复游玩价值

- **三星评价**给了明确的「再玩一次」理由：3 星必须达到求解器算出的最优步数，2 星有 20% 容错。
- 关卡列表直接显示每关星级，首页显示 `★ N / 90` 总星数，形成收集目标。
- 已通关关卡可无限重玩刷星，重试不会清除最佳成绩。
- 每日挑战按当天谜题的最优解评星，并可生成战绩卡分享（不强制、不做排行榜）。

> 以上是设计层面的改进说明。**没有做任何留存、时长或商业表现的数据结论** —— 项目未上线，没有任何真实用户数据。

## 八、下一轮最值得做的三件事

1. **真机验证与性能采样**：装微信开发者工具 + 真机跑 30 关，采集 `wx.getPerformance()` 的启动耗时与帧率，确认电流动画在中低端机上不掉帧（当前只有 Web 端的间接观察）。

3. **接入真实广告并做 A/B**：拿到流量主资格后，先用「失败后 +3 步」这一个激励点位做灰度，观察它对「重试率 / 通关率 / 次日留存」的实际影响，再决定是否加第二个点位——**在没有真实数据前不做任何收益承诺**。
